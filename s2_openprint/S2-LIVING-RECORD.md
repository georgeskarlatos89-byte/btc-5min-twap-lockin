# arena-ai-btc-5-minute new strategies #2 open-print displacement — living record

Every run or change to strategy #2 is logged here as a Part. Same rules as the #1, #3 and #6
records: plain language, no claims without data, no keys or addresses ever.

**What S2 is, in one breath:** when a BTC 5-minute or 15-minute round opens, the price tokens
start near 50¢. If Bitcoin has already moved a few basis points in the first ten seconds, the
idea is that some resting orders near 50¢ are "stale" and have not caught up. S2 does NOT
trade. It is a read-only recorder: ten seconds after each bell it writes down the Chainlink
spot price versus the price at the bell, the 60-second TWAP feed, and the order book on the
side Bitcoin moved toward, then runs the strategy's gates (move of at least 5 bps on 5m / 8
bps on 15m, ask no higher than 60¢, everything less than 2 s old) and logs either a
hypothetical candidate or the reason it skipped. Later, official outcomes are joined and a
replay says what those candidates would have paid at an assumed fee. No wallet, no keys, no
order code exists in the package.

**Where it lives:** `twapvm` (34.34.13.7, NL), folder
`~/#2 open-print displacement/s2_openprint/` (symlink `~/s2_openprint`), own Python venv,
systemd unit `s2-collect.service` (8th service on the box). Package source: this folder's
`s2_openprint/` (= `s2_openprint-research.zip`, byte-identical, 15 files). GitHub:
`georgeskarlatos89-byte/btc-5min-twap-lockin` → `s2_openprint/`.

### The bug: RTDS filters must be compact JSON (verified on two machines)
A 7-minute local capture reproduced the guide's problem exactly: metadata for 3 rounds, 0
ticks on both feeds, 18 empty `{"error": ""}` health lines (the 20 s receive timeout looping,
since `str(asyncio.TimeoutError())` is empty).

Diagnostic, 25 s per variant, same two topics, same symbol, local PC and VM:

| filters string sent | frames per topic (local) | frames per topic (VM) |
|---|---|---|
| `{"symbol":"btc/usd"}` (compact, what the S1 observer sends) | spot 26, twap60 25 | spot 25, twap60 25 |
| `{"symbol": "btc/usd"}` (Python's default `json.dumps`, what the package sent) | 0, 0 | 0, 0 |

The server matches the filter string literally. The package inherited the topic names
correctly (`crypto_prices_chainlink`, `crypto_prices_twap_sixty` both stream, payload keys
`full_accuracy_value, symbol, timestamp, value` and `window_s` on the TWAP) but not the
compact encoding. Snapshot frames (`payload.data[...]`) are correctly ignored.

**Fixes in `capture.py` (plumbing only, no gate touched):** `separators=(',',':')` in the
filter encoding; health errors log the exception class when the message is empty.
`SHA256SUMS` regenerated (capture.py + the adapted service file).

### The finding that matters for the research: the 2-second freshness gate is barely reachable
The gate is "spot timestamp at most 2 s old at decision time", measured against the feed's
SOURCE timestamp. Measured reality: the feed stamps whole seconds, arrives 1.4–1.6 s later,
the sampler runs up to 1 s after the last tick, then fetches the book (~0.2 s). Spot age at
decision therefore lands around 1.8–2.8 s, so most rounds will be skipped as `spot_stale` by
a fraction of a second, exactly as seen (4 of 4 samples so far). I did NOT change the gate:
the guide forbids loosening gates, and whether freshness should be judged on receipt time or
allow ~3 s is a research decision. Until it is made, S2 will collect ticks, books and skip
reasons but produce few or no candidates. Also visible already: 10 s into a round with ~0
displacement, the book was 0.61/0.62, above the 60¢ ceiling, so the "stale 50¢ quotes"
premise is itself something this data will test.

### Telegram wiring (shared `s1_monitor.py`)
Hourly status gains an S2 line with the plain-English description and: ticks per feed and
last-tick age, mean feed lag, samples, hypothetical candidates, skip reasons, health errors,
session restarts, sessions and MB on disk. Urgent pings: no ticks for 3 min while active
(the guide's "connected but blind" failure), health-error storm, more than 3 sessions started
in an hour (restart loop), KILL appears/disappears, service inactive, and one informational
ping per hypothetical candidate (research only, never an order). Offline tests: normal
session → 0 pings; candidate → 1; stale ticks → 1; restart storm → 1.
